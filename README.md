# longtask-context-kit

给**长程 / 无人值守 agent 任务**用的文档体系脚手架 —— 解决"上下文被压缩、会话中途断、交接要重读一大堆"。

## 它是什么

一套**五层分层**的落盘文档结构 + **三条核心纪律**：

| 层 | 文件 | 作用 |
|---|---|---|
| L0.5 | `00_LIVE.md` | **快照**：此刻在做什么（**覆盖式、≤30 行、压缩后第一个读**） |
| L0 | `01_TASK.md` | **任务书**：要干什么 / 铁律 / 坐标 / 读法 |
| L1 | `02_METHOD.md` §0 | **索引**：条目一句话摘要 |
| L2 | `02_METHOD.md` | **条目**：症状→根因→判据→修法 |
| L3 | `03_CASES.md` | **案例**：日志 / 长推演 / 原文（溯源才读） |

**三条纪律**
1. **快照覆盖式、不许过期**（过期的快照比没有更坏）
2. **改库有据**：先查有没有 → 问前人为什么这么写 → 真不对才改且留痕，**不同情况【并存】不覆盖**
3. **跳过 ≠ 通过**：跳过的用例必须标 `NOT-TESTED`，绝不能标 `PASS`

**验收口径**：写进去 → 能查到 → 下一环节看得见（三段证据齐全）。

## 为什么会有这个

长任务最常见的翻车方式不是"技术难"，而是：
> **"不是跑通了吗？我上来怎么就卡住了。"**

根因通常是两条：
- 验收用**老数据自证**（那条路径确实通过，但不是用户走的那条）；
- **跳过项在统计口径里消失**，于是"覆盖率 94/97"纸面成立、真机崩塌。

这套结构把"该记什么、记到哪层、怎么改"制度化，让**换谁来接手都一样**。

## 快速开始

```bash
python scripts/init_task_docs.py ./docs "把 X 系统从零走通到 Y"
```

然后把它接进你的 agent：**开工先读 `00_LIVE.md` → 再读 `01_TASK.md` → 只读指到的那节**；
**收尾必须覆盖重写 `00_LIVE.md`**。

## 和 Obsidian 的关系

同类思路（原子化 + 互链 + 分层），但**读者是 agent**：
它不会"点链接"，只会"按索引定位再读那一段"⇒ 用**索引 + 锚点**比做图谱更省上下文。
